# 自动化动作的真实性核验

## 何时用

- 自动化脚本/机器人跑完了，报表说「成功 N 条」，但你不确定平台侧真的发生了
- 要向上汇报数字，数字必须经得起对方调平台后台核对
- 出现过「本地记成功、平台没有」的虚报，需要修账并防复发

## 核心原则

> **本地记账永远只是「程序以为」，平台回执才是「事实」。**
> 两者不一致时，以平台为准；不一致本身就是 bug，必须能定位是哪一侧。

## 一、证据分级（写进代码判定，不只写在文档里）

| 级别 | 证据形态 | 可信度 |
|---|---|---|
| **A 回执级** | 平台返回的成功文案/状态码/接口 2xx + 资源 id | 可直接记账 |
| **B 界面级** | 页面出现成功提示、列表里出现该条记录 | 可记账，但要处理「提示是通用文案」的误判 |
| **C 行为级** | 点击已提交、请求已发出 | 只能记「已尝试」，不能记「已成功」 |
| **D 推断级** | 由其他现象推测（数量变化、日志无错） | **不可记账** |

判定顺序：能拿 A 就拿 A，拿不到 A 时用 B 并标注来源；**C/D 一律记为待确认**。

## 二、数据模型：给「状态」加可信度字段

- 每条记录加 `verified` 标记：`1` = 有 A/B 级证据，`0` = 历史推测值
- 报表只认 `verified=1`；`verified=0` 的记录只能出现在「待核实」栏
- **历史虚报要能一次性降级**：写一条迁移脚本把这批记录置 0，并保留原值便于比对，别直接删

> 这条比任何算法都重要：一旦「猜的数字」和「真数字」混在一个字段里，后续所有判断都被污染。

## 三、校准探针（定期对账）

1. 用平台自己的「记录/历史」页面或接口拉真值（不是本程序的库）
2. 与本地按 `verified=1` 的计数比对，输出差异清单（多了/少了/状态不符）
3. 差异按类型归因：重复点击、通用成功文案、限速被吞、跳转后未提交、验证码中断
4. 校准结果落库 + 打时间戳，下次比对只看增量

## 四、止损（防止「一直跑一直错」）

- **连续 N 次同点失败**（同一环节、同一原因）→ 自动停，别让重试把额度耗尽或触发风控
- **单轮产出为 0** → 停下来查原因，不要空转到下一轮
- **命中验证/风控页** → 立即停，交人工，不要连续重试（连点只会让后续全部失败）

## 五、验收清单

1. 报告中每个数字都能追到一条 A/B 级证据（点得开、看得见）
2. `verified=0` 的数据不出现在结论区
3. 人为制造一次「点成功但实际未提交」，程序必须记为待确认，而不是成功
4. 连续失败达到阈值会自己停，且留下停机原因
5. 校准一次，差异清单为空或每条差异都有归因

## 反模式

- 用「日志里没有 ERROR」当成功证据
- 用「数量变化」推断成功（可能是重复计数）
- 为了数字好看，把推测值直接写进统计字段
- 发现虚报后直接删记录（失去归因依据，也无法回滚核对）
- 无限重试代替停机
