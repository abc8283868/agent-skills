# 平台 API 批量运维

## 何时用

- 要在平台上批量改配置/批量启停/批量重建，界面点不动
- 要做配置审计（哪些库没启用、哪些分段是空的、参数被谁改过）
- 改之前要先备份、改之后要能证明生效、出事要能回滚

## 铁律

1. **写后必读**：任何 `200/201` 的写操作，立刻 `GET` 回读目标对象比对真值。
2. **批量接口有上限**：常见是「每批 ≤30 条，id 走查询参数」，超长 URL 直接返回 400；按批切分并校验每批返回。
3. **草稿 ≠ 线上**：改的是草稿/编排，必须再走一次发布，线上才生效。
4. **改动前先快照**：导出 DSL / 导出配置 JSON，落到带时间戳的文件里。

## 一、鉴权与最小暴露

- Console API 一般要先登录拿会话（cookie 或 token），再带 `Authorization` 调业务接口
- **凭据不进代码库、不进日志**：用环境变量或本地未提交文件；打印日志时打码
- 服务默认监听 `0.0.0.0` 的本地服务要收口到 `127.0.0.1`（否则同网段可访问）
- 任何「无鉴权就能读密钥/cookie」的调试接口，生产必须关掉

## 二、批量操作模板

```
1. 拉全量列表（分页，记录 total）
2. 本地算差异集（要改的 / 要跳过的），打印条数供人确认
3. 按批 ≤30 切分，逐批提交，每批后校验返回条数
4. 全部提交完，再拉一次全量，逐条比对目标字段
5. 输出报告：成功/跳过/失败/失败原因直方图
```

- **幂等**：每步可用「目标状态」判断（已是目标值就跳过），重跑不会翻车
- **可续跑**：把进度写文件或库，中断后从断点继续，不从头再来

## 三、写后回读的具体写法

- 单条更新：`PUT/PATCH` → `GET` 该对象 → 比对关键字段（如 `enabled`）
- **警惕「静默忽略」**：某些接口对不支持的字段返回 200 但不改；只有回读能发现
- 批量更新：比对「目标集合」与「实际集合」的差集，差集不为空就是失败

## 四、生效时机与一致性

| 改动类型 | 生效条件 |
|---|---|
| 应用配置/编排 | 需发布；只存草稿不生效 |
| 知识库分段/索引 | 需重建索引；旧向量可能残留 |
| 全局参数（默认检索设置） | 立即生效，且**可能覆盖应用内参数** |
| 缓存 | 会话/语义缓存会让你看到旧结果，清缓存再测 |

## 五、验收清单

1. 快照文件存在且能导入回滚
2. 每条改动的目标字段都被回读验证过（不是只看接口返回码）
3. 线上（发布后）行为与配置一致，不只是草稿预览一致
4. 脚本重跑一次不产生副作用（幂等）
5. 失败项都有具体原因，不是笼统的「部分失败」

## 反模式

- 拿「返回 200」当生效
- 一次把所有 id 拼进 URL（400 之后才发现分批问题）
- 在网页上直接点保存，覆盖掉脚本写进去的配置（两边同时改必冲突）
- 改完不发布就下结论「改了没用」
- 凭据/密钥写进脚本提交到仓库
