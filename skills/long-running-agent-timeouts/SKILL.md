# 长任务 Agent 的超时、状态回传与降级

## 何时用

- 聊天机器人/Agent 应用「一直在转圈」「永远在思考」，用户端没有反馈
- 长任务（入库、批处理、多步 Agent）同步等待，连接被中间层断掉
- 需要给一个「卡死了」的系统定责：是客户端、网络还是后端运行时

## 铁律（任何 Agent 交付前先定这四件事）

1. **超时多少**（客户端 + 服务端各一个，服务端必须小于客户端）
2. **超时返回什么**（给用户看的文案，不能是空白或英文堆栈）
3. **失败要不要降级**（换备用模型 / 换个简单链路 / 只回状态不回答）
4. **怎么查状态**（用户能拿到 task_id 或「进度 X/Y」，出事能追）

## 一、先分清「卡」在哪一层（取证顺序）

按证据强度排，不要一上来猜模型：

1. **客户端默认超时**：很多 HTTP 客户端默认超时是 5 分钟甚至无限；表现为「界面无限转圈但没有报错」。取证：查客户端库的超时配置，改成一个能触发的时间，看是否走到错误分支。
2. **服务端是不是还活着**：拿健康检查接口打时间戳。**注意「极慢」和「死了」症状一样** —— 首字节 10 秒以上等于事实不可用（正常应 < 0.1s），此时先查主机负载。
3. **后端运行时卡死**：抓线程栈（Java `jstack`、Python `py-spy dump` / `faulthandler`），看是不是卡在某个锁/连接池/外部调用。
4. **连接被反复重建**：日志里短时间内大量重连（SSE/WebSocket 握手）→ 典型是上游把连接掐了、客户端立刻重连、形成风暴。取证：数单位时间内重连次数。
5. **中间层超时**：网关/反向代理的读超时短于业务处理时间，502/504 但业务其实跑完了（此时会出现「用户看到失败，数据却改了」）。

## 二、修复模板（四层同时做，别只做一个）

- **客户端**：显式超时（如 90s）+ 超时后给出可读提示 + 记录 request_id
- **服务端**：长任务改异步（提交即返回 task_id），前端轮询/订阅进度
- **会话状态**：会话 id 必须落库（否则「多轮记忆」永远是假的，每次都是新会话）
- **降级**：主链路超时 → 换备用应用/模型 → 仍失败则明确告知「已受理，稍后回」

## 三、会话记忆这类高频坑

- 会话 id 只存在内存/请求上下文 → 进程重启或换实例后丢失，表现为「它记不住上一句」
- 上游返回了 conversation_id 但代码没取、没存 → 同理
- 取证：打印每次请求携带的会话 id，看是否为同一值

## 四、验收清单

1. 人为制造慢响应（sleep）：客户端在约定时间给出可读错误，不是无限等待
2. 进程被重启：会话记忆仍在（id 从库里读出来）
3. 上游不可用：走降级分支，用户看到明确状态
4. 长任务中途失败：状态表里能看到 failed + 原因，可重试且**不重复产生副作用**（幂等键）
5. 日志里能按 request_id / task_id 串起一次完整调用

## 反模式

- 只调大客户端超时，把问题藏起来
- 超时后静默返回空字符串（用户以为系统坏了）
- 用「重试」代替幂等：重试三次产生三笔记录
- 把「首字节 13 秒」当成「服务器没死所以没问题」
